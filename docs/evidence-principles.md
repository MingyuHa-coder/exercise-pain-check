# 근거 표시 원칙

이 프로젝트의 핵심 원칙. 앱과 기획서의 모든 내용을 아래 네 가지 중 하나로 구분해서 보여준다. AI가 운동법을 추천하는 앱이 아니라, 근거의 출처와 한계까지 투명하게 보여주는 운동 문제 해결 플랫폼을 만들기 위해서다.

| 구분 | 앱 표시 | 뜻 | 예시 |
|---|---|---|---|
| 1. 논문에서 직접 확인된 사실 | 논문 확인 | 논문 본문에서 직접 확인한 결과. 대상·규모 같은 한계를 함께 적는다 | 건강한 11명에서 1.7배 그립은 어깨 회전력을 키웠다 (Gundersen 2026) |
| 2. 여러 연구를 종합한 해석 | 연구 종합 해석 | 여러 연구를 묶어 내린 해석. 결과의 "점검할 운동 변수" 설명이 여기에 속한다 | 팔을 머리 위로 올리는 구간의 어깨 부담 |
| 3. 연구를 바탕으로 한 실용적인 조정 | 앱 제안 | 1·2를 바탕으로 앱이 권하는 구체적인 행동 | 앞으로 내리는 프레스로 바꾸기 |
| 4. 아직 검증되지 않은 자체 가설 | 검증 안 된 가설 | 앱이 정한 값·기준·연결. 전문가 검토와 연구가 필요한 부분 | 아픈 사람에게 1.4배 그립이 가장 낫다 / 혼자 한 통증 호 검사도 정확하다 |

## 적용 규칙

- 논문에 어떤 값이 나왔다고 해서, 그 값이 앱의 상황(통증이 있는 사람, 혼자 해 보는 검사)에서도 맞다고 쓰지 않는다. 그 연결은 4번이다.
  - 예: Gundersen 2026은 1.0·1.4·1.7배를 비교했지만, 통증이 있는 사람에게 1.4배가 최적이라는 결론은 없다.
  - 예: Michener 2009의 통증 호 60~120° 기준은 진료실에서 검사자가 한 결과다. 사용자 혼자 해도 정확한지는 검증되지 않았다.
- 조정 카드는 "앱 제안 / 논문 확인 / 검증 안 된 가설"을 나눠서 보여준다.
- 결과 카드는 질환명이 아니라 운동 변수로 제목을 붙인다(기획서 6-3). "연구 종합 해석"이고, 그 아래 근거(논문 확인)와 한계(가설)를 따로 붙인다. 연구에서 쓰는 이름(질환명)과 진단 가능성 문장은 사용자 화면에 보여주지 않고 내부 검토 자료로만 보존한다(v8). 의학 용어 모드도 해부학 용어만 바꾼다.
- 질환명이 연구 대상인 근거를 사용자에게 보여줄 때는 "진료에서 ~로 분류된 사람", "진찰로 ~이 확인된 사람"처럼 써서 대상을 실제보다 넓히지 않는다. 원래 질환명과 대상은 내부 자료(`docs/user-wording-changes.md`, `content/studies.js`의 `who`)에 둔다.
- "논문 확인" 아래에는 근거 수준을 붙인다: 연구 종류 · 대상(인원) · 앱 이용자와의 거리("통증 있는 사람 대상" / "건강인·선수·모델 등에서 옮김" / "진료 지침·합의"). 연구별 분류는 `content/studies.js`에 있다.
- 사용자에게 검사 동작을 직접 해 보게 하지 않는다. 이미 겪은 운동 상황만 묻는다(기획서 3-1 ③).
- 치료·재활·처방처럼 들리는 표현은 앱 목소리로 쓰지 않는다(기획서 6-4). 논문이 한 말을 옮길 때만 근거 설명 안에 쓴다.
- 점수 규칙, 기간, 우선순위처럼 앱이 정한 값은 모두 4번이다. 근거나 전문가 검토가 없는 기간·수치를 새로 만들지 않는다(v8에서 "2주"와 C9 기준 점수 제거). 전체 목록은 `docs/rule-inventory.md`.
- 전문가 검토 상태는 실제 검토 기록이 있을 때만 바뀐다. 검토 완료는 분야와 범위를 함께 표시하고, 전체가 검토된 것처럼 보이는 표현은 쓰지 않는다.
- 4번 항목은 [전문가 검토 대기 목록](expert-review-pending.md)에 모아서 한 번에 검토받는다.
- 새 주제를 추가할 때도 유료 논문까지 조사하고, 본문을 확인한 자료만 1번으로 쓴다.
