# 근거-판단 규칙 추적 (audit)

앱의 운동 조정이 **어떤 질문 → 어떤 점수 규칙 → 어떤 결과 변수 → 어떤 조정 후보 규칙**을 거쳐 나오는지, 그리고 그 과정의 카드에 **어떤 연구가 인용됐는지** 추적하는 자료다. Work(독립 문헌 조사)의 결과를 앱 코드와 연결하기 위해 만들었다.

- 이 폴더의 `<주제>-*` 파일은 **스크립트가 코드에서 자동으로 만든다.** 직접 고치지 않는다.
- 의학적 판단, 근거 등급, 새 기준은 담지 않는다. 앱 코드에 적힌 것을 옮기고, 코드에서 확인할 수 없는 것은 **수동 검토 필요**로 남긴다.
- 판단 규칙 전체 목록과 분류(①②③)는 [../rule-inventory.md](../rule-inventory.md)에 있다. 여기서는 그 규칙들을 ID로 나눠 근거와 연결한다.

## 파일

| 파일 | 내용 |
| --- | --- |
| `bench-traceability.md` | 질문·답 → 점수 규칙 → 변수 선택 → 조정 후보·우선순위 → 공통 마무리. **연구별 역추적**(7장), 한 답만 바꿨을 때 결과(8장), **검증 수준·규칙별 동작 확인 상태**(10장), Work 자료 연결(11장) |
| `bench-evidence-links.csv` | 연구 1개 × 인용 위치 1곳 = 한 줄. 앱 문장, 근거 표시 유형, 관련 변수·조정·규칙·질문, Work 칸(비어 있음) |
| `bench-review-questions.md` | 전문가 검토가 필요한 규칙별 질문 (검토 목록 번호와 연결) |
| `bench-new-study-links.csv` | Work가 새로 찾은 연구(`new:`) × 연결한 앱 주장·규칙 한 줄. Work 자료가 없으면 머리줄만 있다 |
| `bench-trace.json` | 위 내용을 기계가 읽는 형식. **판단 규칙의 기준 자료**이기도 하다 (검증이 지금 코드와 비교) |
| `evidence-matrix-template.csv` | Work가 채울 Evidence Matrix 양식 |
| `new-studies-template.csv` | Work가 새로 찾은 연구 목록 양식 |
| `work/` | Work 결과를 넣는 곳 (`<주제>-evidence-matrix.csv`, `<주제>-new-studies.csv`) |

도구 쪽 파일: `tools/audit/cases/<주제>.json`(손으로 계산한 고정 사례), `tools/audit/manual/<주제>.json`(사람이 적은 설명·검토 목록 연결), `tools/audit/test-audit.js`(재현 테스트).

## 다시 만들기와 검증

```bash
node tools/audit/build-trace.js --topic bench    # 자료 다시 만들기
node tools/audit/verify-trace.js --topic bench   # 코드와 자료가 맞는지 검사 (틀리면 종료 코드 1)
node tools/audit/test-audit.js                   # 추적 시스템 자체의 재현 테스트 (임시 폴더에서 일부러 틀리게 만들어 봄)
```

`node tests/run-tests.js`를 돌리면 위 두 검사도 함께 돈다.

### 검증 수준 — 세 가지를 구분한다

| 수준 | 무엇을 확인하나 | 한계 |
| --- | --- | --- |
| 해석 대조 | 코드에서 읽어 낸 점수·후보 규칙으로 계산한 값이 실제 `analyse()`와 무작위 답 50,000개에서 같은지 | 해석이 코드를 그대로 따라가므로, **코드를 일부러 바꿔도 해석도 같이 바뀌어 통과한다.** 독립 확인이 아니다 |
| 최종 결과 독립 모델 | 변수 선택·우선순위 정렬·상위 3개·0점 변수 제외·좁히기 어려움·진료 먼저를 문서에 적힌 규칙대로 따로 계산해 실제 결과와 비교 | 선택 줄 해석은 코드를 따른다. 공통 마무리(`finish()`)는 독립 계산이라 `finish()`가 바뀌면 불일치로 드러난다 |
| 고정 사례 (`tools/audit/cases/<주제>.json`) | 사람이 **손으로 계산한** 기대 결과와 실제 결과가 같은지. 같은 점수, 기준 점수 바로 위·아래, 조정이 하나도 없는 경우, 후보 6개 중 3개, 진료 먼저 조건 등 경계와 특정 답 조합 | 사례에 없는 조합은 확인하지 않는다 |

여기에 **기준 자료 비교**가 더해진다: 지금 코드의 점수·우선순위(조건부 우선순위 포함)·후보 조건·선택 줄·공통 규칙·진료 먼저 조건을 `bench-trace.json`과 하나씩 비교해 `bench.P.grip 우선순위 2 → 8`처럼 무엇이 바뀌었는지 알려 준다. 판단 규칙을 바꾸려면 전문가 검토를 거친 뒤 자료를 다시 만들고 고정 사례 기대값을 **손으로 다시 계산**해야 검증을 통과한다.

규칙마다 `bench-traceability.md` 10장에 상태가 붙는다.
- **동작 확인**: 고정 사례가 그 규칙을 지나고, 해석·모델 대조도 맞음. 코드가 적힌 대로 동작한다는 뜻일 뿐 **의학적으로 맞다는 뜻이 아니다.**
- **수동 검토 필요**: 고정 사례가 없거나, 이 주제에서는 확인할 수 없거나(예: 벤치프레스에는 `referOnly` 변수가 없음), 해석 대조만 있는 경우. 검증 완료로 세지 않는다.
- **실패**: 고정 사례 결과가 기대와 다름.

그 밖의 검사: 자료가 최신인지, `analyse()`의 모든 줄을 해석했는지, 모든 질문·답·출처·카드가 자료에 있는지, 파일 위치가 실제 문장을 가리키는지, 규칙 ID가 모두 실제로 있는지, 수동 연결 대상이 있는지, 검토 기록이 0개 그대로인지, 앱 화면이 추적 자료를 불러오지 않는지, Work 자료의 ID·연결이 올바른지.

### 무작위 답 빈도는 실제 이용자 빈도가 아니다

추적표의 "무작위 답에서 나온 비율"은 모든 답을 **똑같은 확률로 고른 가상의 답** 50,000개에서 센 값이다. 실제 이용자가 어떤 답을 고르는지, 실제로 어떤 조정을 얼마나 받는지와는 관계가 없다. 규칙이 한 번도 안 쓰이는지, 특정 조정이 지나치게 몰리는지 같은 **코드 동작 점검용**으로만 쓴다.

## Work의 Evidence Matrix와 연결하기

1. `evidence-matrix-template.csv`를 복사해 `work/<주제>-evidence-matrix.csv`로 저장하고 Work가 채운다.
2. 앱이 인용한 연구는 `study_id`에 위 연구 ID를 그대로 쓴다(기존 ID·연결은 바꾸지 않는다).
3. **Work가 새로 찾은 연구**는 `new-studies-template.csv`를 복사한 `work/<주제>-new-studies.csv`에 먼저 등록한다.
   - ID는 `new:소문자-숫자-하이픈` (예: `new:kim-2025-bench-grip`). 앱 인용 연구 ID와 겹치면 안 된다.
   - DOI·PMID·제목 중 하나는 반드시 적는다. 형식이 틀리거나, 같은 DOI·PMID를 두 번 등록하면 검증이 막는다.
   - 행렬에서는 그 `new:` ID를 `study_id`로 쓴다. 등록하지 않은 ID는 검증이 막는다.
   - 앱 출처 목록에는 DOI가 없어서, 신규로 등록한 연구가 사실 앱이 이미 인용한 연구인지 자동으로 확정할 수 없다. 저자·연도가 같으면 검증이 **사람이 확인하라는 알림**을 띄운다.
4. 특정 인용 위치에 대한 결론이면 `location_id`, 특정 판단 규칙에 대한 결론이면 `rule_ids`(공백으로 구분)를 적는다.
5. `node tools/audit/build-trace.js`를 다시 실행하면 근거 연결표의 `work_*` 칸과 `bench-new-study-links.csv`에 Work 결과가 붙는다.

**Work 자료를 넣어도 앱의 근거 표시·근거 등급·사용자 문구·검토 상태는 자동으로 바뀌지 않는다.** 재현 테스트가 Work 자료를 넣은 뒤 앱 파일이 그대로인지 확인한다.

### 세 가지를 섞지 않기

| 무엇 | 어디에 | 예 |
| --- | --- | --- |
| 1. 논문이 **존재**하는지 | 신규 목록 `existence_checked`(Y/N), `existence_source` | DOI로 서지 확인 |
| 2. 논문이 **무엇을 보고**했는지 | 행렬 `finding_type`(E0~E4·E9), `finding_text` | 아래 표 |
| 3. 그 결과가 **앱 주장과 어떤 관계**인지 | 행렬 `relation_to_app`, `relation_note` | 아래 표 |

존재만 확인한 연구(E0)로는 지지·반박·간접 근거를 기록할 수 없다(검증이 막는다). 관계를 적으면 대상(`location_id` 또는 `rule_ids`)과 보고 내용(`finding_text`)도 있어야 한다.

### 앱과의 관계 (`relation_to_app`)

| 코드 | 뜻 |
| --- | --- |
| `support_direct` | 직접 지지 — 같은 대상·같은 상황에서 앱 주장과 같은 결과를 보고 |
| `contradict` | 반박 — 앱 주장과 반대되는 결과를 보고 |
| `indirect` | 간접 근거 — 관련은 있지만 대상·상황·결과 종류가 다름 (예: 생체역학 결과로 통증 감소를 말하는 경우) |
| `not_applicable` | 적용 어려움 — 대상·설계가 달라 앱 주장에 쓰기 어려움 |
| `undetermined` | 판단 보류 — 아직 정하지 않음 (대상 없이 적어도 됨) |

관계를 정하는 것은 Work와 전문가 검토의 몫이다. 이 도구는 값이 목록 안에 있는지와 연결 대상이 실제로 있는지만 검사한다.

### 결과 종류를 섞지 않기 (`finding_type`)

| 코드 | 뜻 | 예 |
| --- | --- | --- |
| E0 | 논문이 존재하고 서지 정보가 맞음 (내용 판단 없음) | 인용 정보 확인 |
| E1 | 논문이 측정·생체역학 결과를 보고함 | 모델에서 그립 너비에 따라 관절 부하가 달랐다 |
| E2 | 논문이 특정 조정·치료의 통증·기능 효과를 보고함 | 무작위 대조 시험에서 운동으로 통증이 줄었다 |
| E3 | 논문이 요인과 증상·소견의 연관을 보고함 (원인·진단 판단 아님) | 1RM이 높을수록 MRI 소견이 많았다 |
| E4 | 지침·합의문의 권고 | 진료 지침 권고 |
| E9 | 기타·분류 어려움 | |

- 앱 문장이 무엇을 주장하는지(`claim_category`)는 근거 연결표에서 **수동 검토 필요**로 비워 두었다. Work 결과와 비교할 때 사람이 채운다. 예: 앱 문장은 E2(효과)처럼 읽히는데 Work 결과는 E1(측정)뿐이면 불일치다.
- `work_grade`(근거 등급)는 Work만 채운다. 이 도구와 앱 코드는 근거 등급을 매기지 않는다.
- 근거 연결표의 `study_type_in_app`, `population_in_app`은 **앱에 적혀 있는 값**(`content/studies.js`)이고 Work가 확인한 값이 아니다.

## 자동으로 할 수 있는 것과 없는 것

| 자동 | 수동 검토 필요 |
| --- | --- |
| 질문·답 목록, 점수 규칙, 조정 후보 조건·우선순위 숫자 (단순 형태: `if (has(..) \|\| has(..)) sc.X += N`, `picks.push`) | 변수 선택 줄의 뜻 설명 (코드 원문은 자동, 설명은 `tools/audit/manual/<주제>.json`) |
| 해석 결과를 실제 `analyse()`와 대조 | `&&`·중첩 조건 등 지원하지 않는 형태의 줄 (검증이 실패로 알려준다) |
| 인용 위치(파일:줄)와 출처 문자열 → 연구 ID 연결 | 출처가 2개 이상인 문장에서 어느 부분이 어느 연구인지 |
| 카드·조정 → 관련 규칙·질문 경로 (코드 경로) | 연구 목록에 없는 출처의 연구 종류·대상 |
| 무작위 표본 빈도(코드 점검용, 실제 이용자 빈도 아님), 한 답만 바꿨을 때 결과 | 앱 문장이 주장하는 결과 종류(E0~E4), 근거 등급, 앱과의 관계 |
| 우선순위 숫자·조건부 우선순위·선택 줄이 기준 자료와 같은지, 고정 사례 결과 | 고정 사례가 없는 규칙의 동작, 같은 우선순위 숫자끼리의 순서(벤치프레스에는 없음), `referOnly`(벤치프레스에는 없음) |
| 신규 연구 ID·DOI·PMID 형식, 중복, 등록 여부, 관계 값·대상 유효성 | 신규 연구가 앱 인용 연구와 같은 논문인지(앱 출처에 DOI 없음), 논문 존재 여부 자체 |
| 검토 목록 번호(B·C)와 규칙 ID 연결이 유효한지 | 그 연결 자체 (`manual/<주제>.json`) |

## 나머지 12개 주제로 넓히기

1. `node tools/audit/build-trace.js --topic <주제>`를 실행해 해석 못 한 줄이 있는지 본다. 주제마다 `analyse()` 형태가 조금씩 다르다(예: 점수 순서로 정렬하는 `order`, 위치 하나로 정하는 규칙, `main === "side"` 같은 조건부 후보).
2. 해석 못 한 형태는 `tools/audit/lib.js`의 `parseAnalyse()`에 형태를 추가하거나, 그 줄을 수동 검토로 남긴다. 추가한 뒤에는 반드시 무작위 대조가 0건 불일치인지 확인한다. 변수 선택 줄 형태가 `parseSelection()`에 없으면 최종 결과 독립 모델을 만들지 않고 **수동 검토 필요**로 남긴다.
3. `tools/audit/cases/<주제>.json`에 고정 사례를 손으로 계산해 적는다. 코드를 돌려서 나온 값을 그대로 적으면 독립 확인이 아니다.
4. `tools/audit/manual/<주제>.json`에 선택 규칙 설명과 검토 목록 번호 연결을 사람이 적는다.
5. 같은 변수·조정을 함께 쓰는 주제(데드리프트 ↔ 스쿼트 허리 ↔ 바벨 로우, 숄더 프레스 ↔ 레터럴 레이즈, 어깨 공통 `COMMON_P.rc`·`COMMON_A.acc`)는 근거 위치 ID가 같은 코드 위치를 가리키므로, Work 결론 하나가 여러 주제에 영향을 준다. 주제를 넓힐 때 연구별 역추적을 주제를 가로질러 합치는 표(`all-studies.md`)를 추가하는 것을 권한다.
6. `tests/run-tests.js`의 추적 검사 줄에 주제를 추가한다(지금은 bench만).
